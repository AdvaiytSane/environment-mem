# Critique 1: warm vs HackMIT judging and Cognition

Read against PLAN.html, the sponsor challenge text (COGNITION, OPENAI, THE TOKEN COMPANY, WARP), the HackMIT Code of Conduct, and public Devin/Cognition documentation and blog posts as of 2026-09-19.

## 1. Top 5 reasons this loses at HackMIT judging (Innovation 30, Technical 30, Impact 30, Learning 10)

**1. The demo is a spreadsheet, not a product a judge can feel.** The on-screen artifact is a table: tokens, tool calls, seconds, cost, cold vs warm, times 9,000. Impact points go to things a judge can see change a real workflow in the two minutes at your table. A benchmarking table only lands with someone who already runs an agent fleet, which is not most of the judging pool. What would refute this: a live, timed, side by side run where a judge watches a cold session grep around and misconfigure something, then watches a warm session go straight to the fix, stopwatch visible. Without that literal side by side, the pitch stays a spreadsheet.

**2. The core loop already ships in Devin, so Innovation is at risk before the pitch starts.** Devin Skills already do: session discovers a setup or test procedure, Devin auto-suggests a reusable `SKILL.md`, it gets committed and reviewed via PR, then it's auto-discovered and injected as a system-level instruction at the start of future sessions. Devin Knowledge already does: auto-suggest items from session feedback, retrieve them contextually rather than dump them all at once. DeepWiki already auto-generates architecture docs, module explanations, and dependency maps for any repo, no setup. A judge who spends five minutes on docs.devin.ai (this review did) finds all three shipped. Claiming to invent "capture what a session learned, hand it to the next session" to the company that already ships that loop is a fast way to lose the Innovation score. What would refute this: naming the prior art in the pitch itself and stating the actual delta, for example: cross-harness capture from one hook format (Claude Code, Codex, Devin) versus Devin Skills being Devin-only; automatic zero-touch capture versus Devin's suggest-then-approve; deterministic extraction versus Devin's LLM-based suggestion.

**3. The technical core is a log formatter, and judges will see it as that.** "Deterministic, trace in, procedure out, no model call" means the extractor is a rule-based grouping of tool-call logs into read, search, write, execute buckets. That is fine engineering but it is not a novel algorithm, retrieval system, or anything a Technical judge weighs against multi-agent orchestration or a custom eval harness from a neighboring table. What would refute this: showing the hard part is inferring preconditions (what was read before the first successful write) and postconditions (what command verified success) well enough that the agent's behavior measurably changes because of that structure, not just because it saw more text in its context.

**4. The Learning score depends on a stopping rule that can be satisfied by noise.** The plan's own loop is: "read the warm traces, find what the agent still re-discovers, tighten extraction or injection, rerun. Stop when warm tool calls stop falling." With three repeats per cell and six tasks total, a flat or falling curve is easy to produce by chance (see section 3). A monotonic improvement curve with no reported failure reads as cherry-picked, and Learning is graded on whether the team can show real iteration, not just a chart that goes down and to the right. What would refute this: one paragraph naming a specific thing that did not work and why (for example, "we tried injecting the full trace, it made the agent worse because X, so we switched to structured pre/postconditions"), which is more credible than a clean curve.

**5. The sponsor map itself reads like the "startup wrapper" risk the plan already flagged.** A CLI whose main differentiator is an optional, off-by-default adapter to a company the founder already runs, paired with a demo whose central artifact is a savings table, matches exactly what judges are primed to distrust after the Code of Conduct briefing. What would refute this: never enabling the adapter in front of judges, and pointing at a git log with weekend-only timestamps before being asked, not after.

## 2. Top 5 reasons Cognition says no or shrugs

**1. The mechanism already ships as Devin Skills and Knowledge auto-suggest.** Skills: "any repeatable workflow you want Devin to follow consistently," authored as `SKILL.md`, auto-suggested when Devin "tests your application or learns something new about your setup," proposed with a Create PR button, injected as a system-level instruction at session start or via `@skills:name`. Knowledge: auto-suggested from chat feedback, retrieved contextually, not preloaded. A Cognition engineer's first reaction to "we capture what a session learned and hand it to the next session" will be "we ship this." The rebuttal has to be pre-loaded (cross-harness, zero-touch, deterministic, not Devin-authored) or this is a fast no.

**2. Warm-start on a fleet is probably not the cost driver Cognition means by "saving."** Cognition's own 2026 cost story is Fusion: two models running in parallel, a frontier "lead" and a cheap "sidekick," with a lightweight classifier switching models mid-session at compaction boundaries to avoid extra cache misses. Cognition states this cuts cost roughly 60% on real usage and that the router fully automates 88% of Cognition's own merged PRs. That is a model-routing lever pulled inside a session. It has nothing to do with whether the session had to re-discover the repo. If "saving" is the word the Cognition person used, this is very likely what they meant, and it does not overlap with what warm measures.

**3. Devin bills in ACU, not tokens, and the plan's numbers do not translate.** An ACU bundles VM time, model inference, and network, at roughly $2 to $2.25 each, with a rule of thumb of about 15 minutes of active work per ACU. A pitch built on "input tokens before first edit" does not automatically translate into ACU or dollar savings for a real Devin customer. Reading tokens can be prompt-cached and cheap in wall-clock terms even when the token count looks large, and it is wall-clock and VM time, not token count, that the ACU meter is running on. The team needs the story in ACU-minutes, and as written it is not.

**4. "Context management at 9,000 sessions" almost certainly means something other than procedure injection.** Three more likely readings, all with more support in Cognition's own public material than "the agent forgot how to run the tests": (a) VM and sandbox warm-pool economics, Cognition's own use of the word "warm" already refers to keeping sandbox containers pre-provisioned to avoid cold-boot latency, a live tradeoff (pay for idle warm pools versus unpredictable cold-start delay) they discuss and just shipped a partial answer to in July 2026 with Devin Outposts, which moves execution off Cognition's own infrastructure entirely; (b) prompt-cache hit rate across a burst of concurrent sessions sharing a prefix, since Fusion's own design explicitly engineers around 5-minute cache-expiry windows; (c) the orchestrator's own context load when a parent Devin manages thousands of children, since Devin already reads the full trajectories of its managed Devins to learn what worked and improve the next task breakdown, an existing cross-session learning loop at the fleet-management layer, not the repo layer. If the team cannot say on the spot which of these three was meant, they are answering a question that was not asked. Given the person also said memory was "not the main thing," reading (a) is the most likely: they may have been asking about VM cost, not agent memory, in the same breath.

**5. Hooks are not the seam Cognition has built out for "teach Devin something once, reuse it."** That seam is Skills and Knowledge: git-committed, PR-reviewed, macro-invoked, with a settings page and a team workflow. Hooks in Devin's own docs are positioned for permission gating (block, allow, ask on a tool call), not for surfacing a learned procedure to a team. A capture pipeline that lives entirely in a hook file and writes to a JSONL blob has no equivalent visibility inside the product Cognition sells. Even if it works, it is invisible in exactly the place Cognition already has a first-party, promotable answer.

## 3. Eval design holes

- **Same-shape tasks may be near-duplicates, not independent discovery problems.** Six tasks across three shapes means two tasks per shape. Warm-task-2 gets the procedure extracted from cold-task-1 of the same shape. If the two tasks in a shape are close (add flag `--verbose` versus add flag `--dry-run`), the warm run is not skipping generic repo discovery, it is reusing a near-complete solution to a near-identical problem, which is a known and unremarkable few-shot effect, not evidence that procedure capture generalizes. This is the single most likely thing a technical judge or a Cognition engineer probes first. Check: how different are the two tasks inside each shape, concretely.
- **n=3 is too small for wall-clock and tool-call variance.** LLM agent sessions vary run to run: retries, different exploration paths, transient tool errors. Three repeats per cell can produce a large apparent effect from one unlucky cold run or one lucky warm run. No variance, range, or significance is reported in the plan. Report median and spread, not just a mean delta, or the number is not defensible under a follow-up question.
- **Small, possibly adversarially-shaped fixture.** The plan's own risk list already flags that discovery savings need a repo big enough to matter (a few hundred files, a non-obvious test command). The failure mode not listed: building that fixture to be painful to discover, specifically to make the cold column look bad, produces a number that is true of the fixture and not representative of a normal repo.
- **No baseline against a static doc.** The obvious cheaper alternative to a live capture-and-inject pipeline is a one-time AGENTS.md, CLAUDE.md, or a DeepWiki-style generated doc, pointed at by every session. The eval as designed only compares cold (nothing) against warm (injected procedure). It needs a third arm: cold plus a static doc, so the reported number is the marginal value of dynamic capture over the much cheaper static alternative, not the value of dynamic capture over nothing. Nothing is not the real competitor.
- **Prompt caching confound.** Anthropic, OpenAI, and Devin's own Fusion harness all cache on stable prefixes. Injecting the procedure via `additionalContext` at SessionStart changes the prompt prefix between cold and warm runs, and across the three repeats of a warm cell, later repeats may get cheaper purely from a cache hit on the injected text itself, independent of whether discovery was actually skipped. Report cache read and write tokens separately, or the "token savings" number conflates two different mechanisms.
- **The metric family changes when the runner changes.** `claude -p --output-format json` reports tokens and a dollar cost estimate. Devin bills in ACU, a bundle of VM time, inference, and network, not tokens. The ATIF export apparently carries token-level data normalized to a cost estimate via a third-party model-pricing table, which is a modeled number, not Devin's actual invoice line. If Devin CLI login does not happen before judging, every number at the venue is a Claude Code proxy, and the fleet-of-9,000 projection is a projection of a projection, twice removed from anything Devin bills.
- **Tests-pass on n=6 total tasks is too small to claim reliability.** One flipped test out of six is already a 17-point swing in the reported pass rate. "Must not drop" needs more than six tasks to say anything.

## 4. Code of Conduct, line by line against this plan

- "Qualified entries are restricted to those started within the hackathon hours. Projects that contain code written before the official hacking start time will be disqualified; however, exceptions to this rule are made for publicly available open-source code and libraries." The plan states everything in the `warm` repo is written this weekend, which covers the CLI itself. Two things sit outside that clean statement: (1) building a fixture with "a few hundred files" and a deliberately non-obvious test command, during the event, alongside the actual CLI, is a real time cost, and there is a temptation to prepare that fixture ahead of the clock starting to protect build hours, which is exactly what this clause targets; (2) the `memorable` adapter shells out to a CLI (`memorable ingest`, `memorable recall`) that predates the event by a long way. The carve-out in this clause is specifically for "publicly available open-source" code. Memorable CLI is described elsewhere as public-npm with an EULA license, not open source. Disclosing a dependency (satisfying the separate "undisclosed library" clause below) does not by itself satisfy this clause, because the exception here is written narrowly around open source, not around "disclosed."
- "Submission of another group's or individual's work is considered cheating." Memorable is the founder's own prior company, not someone else's work in the literal sense, but a judge reading "shells out to a company the founder already runs" without that context will read it the same way this clause is written to catch. The mitigation only works if the adapter is never enabled during judging and the founder's relationship to Memorable is stated up front, not left for a judge to discover.
- "Any undisclosed library or API is cheating... misrepresentation of your hack, accidental or not, is considered cheating." The plan's mitigation, naming the adapter in the Plume write-up as off by default, satisfies this clause on paper. It only holds if the live demo and the pitch never imply persistent, cross-session, Memorable-powered memory when the numbers on screen came from the plain JSONL path. Any slide or spoken line that leads with "memory" risks exactly this.
- "The HackMIT team reserves the right to disqualify projects for other forms of cheating not explicitly specified here." A generic catch-all. Combined with the plan's own noted risk ("judges may read it as a startup wrapper"), this is the clause that turns a borderline presentation choice into an actual disqualification if a judge decides the weekend framing is not credible.
- Eligibility ("currently enrolled undergraduate and MIT M.Eng students who are at least 18") is a hard gate independent of the project's quality. Nothing in the plan or repo confirms team eligibility; this should be checked directly rather than assumed.
- Badge, sleeping, and harassment sections are not applicable to the project itself.

## 5. The strongest version of this idea

- **Drop the word "warm" when talking to Cognition.** Cognition's own vocabulary already uses "warm" for sandbox pool provisioning (keep containers running to avoid cold-boot latency, the tradeoff their Devin Outposts feature was built to dodge). Using the same word for procedure injection invites exactly the confusion the booth conversation already showed signs of. Keep the repo name if it is already committed, but open the pitch with a sentence that draws the line: not sandbox warm-up, what happens after the sandbox is already up and the model starts reading files.
- **Put Skills, Knowledge, and DeepWiki in the demo, not around it.** Show a row for "static AGENTS.md," a row for "DeepWiki-style one-time doc," and a row for the captured procedure. Lead with the gap between the second row and the third, not with cold versus nothing. This turns the biggest threat, redundancy, into the actual finding.
- **Re-target the seam: feed Skills instead of competing with them.** Devin already auto-suggests a `SKILL.md` after a session learns something, with a human clicking Create PR. Position the deterministic extractor as the thing that writes that PR automatically, and that also runs for Claude Code and Codex sessions that never touch Devin's own suggestion pipeline. The pitch becomes "we keep Skills current across every harness, not just Devin," which answers "we already have Skills" with "yes, and this is what fills them in without anyone clicking a button."
- **Report the number in ACU-minutes, not tokens.** Translate the wall-clock delta using the roughly 15-minutes-per-ACU rule, so the number is stated in the currency Devin customers are actually billed in.
- **Add the static-doc control arm to the eval**, increase repeats and report spread, and pick two genuinely different tasks per shape so the near-duplicate objection cannot be raised.
- **For The Token Company specifically**, their own text says they mainly want savings inside the shipped product, not savings made while building it, with creative building-time savings accepted as a secondary case. Either do not lead with this sponsor, or add a second, real in-product saving: make `warm recall` a deterministic match with no model call at all, and report that as the actual LLM-cost saving inside warm's own stack, separate from the fleet story.

## 6. Three questions for the Cognition person at the booth

1. When you said "not so interested in memory, more interested in saving," and "when we spawn 9,000 VM sessions, what happens to context," were you talking about sandbox and VM provisioning cost, model context window and compaction, or something else? Which layer.
2. Is the number you'd actually look at input tokens before the first edit, or session wall-clock and ACU (VM plus inference plus network, bundled)? Which of the four columns in a cold-vs-warm table would you check first.
3. If something like this were useful to you, would it plug in as something that writes and updates Skills and Knowledge automatically, as a separate hook-only layer specific to Devin CLI, or is this actually out of scope for Devin and only relevant to Claude Code and Codex fleets?
